## Blockers (fix before the tag)

### B1. Non-composed events from slotted light-DOM content run every `on()` handler twice (three times when nested). Verified.

`src/bind.ts:890` (`handleShadowEvent`), reached through `src/component.ts:2878` (`delegateShadowRoot(shadow)`).

- **Cause:** #4160 adds a capture listener to every shadow root a Component attaches. That listener calls `handleBoundEvent` whenever `!event.composed`. A slotted light-DOM node's event path still passes through its assigned slot and the shadow root, because the node's own root is the document. So a non-composed `change` or `submit` reaches both the `<body>` listener and the shadow-root listener. Both runs climb `parentElement` from the same `event.target` and run every handler on the element and its light ancestors. Each further enclosing shadow root adds another run.
- **Measured:** the committed dist in Chromium and Firefox gives slotted input = 2, light ancestor `onChange` = 2, nested slot = 3. v1.10.11's dist gives 1 / 1 / 1. The bug is silent unless a handler calls `stopPropagation`.
- **Impact:** shadow Components that wrap slotted form controls are common in tosijs-ui. With this bug a submit posts twice, a toggle undoes itself, and a counter double-counts.
- **Why the suite is green:** Happy DOM does not route slotted events through the shadow root (the probe fired once). Any unit test of this case would pass without testing anything.
- **Fix:** in `handleShadowEvent`, run the handler only for events that started in that root:
  ```
  if (!event.composed && (event.target as Node).getRootNode() === event.currentTarget) handleBoundEvent(event)
  ```
  For a slotted origin, the root node is the document, so `<body>` handles the event alone.
- **Clears when:** a **browser-lane** test passes: a `.pw.ts`, or a ```` ```test ```` doc block run by `doc-tests.pw.ts`. It should slot a light `<input onChange>` into a shadow Component, plus a nested two-level variant and a light-ancestor handler, dispatch a non-composed `change`, and assert exactly one call each. Run it with the fix reverted and confirm it fails. Keep the existing #4160 cases (composed handled once, delegation stops at the root) green.
- **Re-review scope:** correctness and blast-radius over the `bind.ts` remediation diff only, verified in the browser lane. Per the CLAUDE.md browser-lane caveat, build, then commit `dist/`, then run the browser lane, then build again. The lane reads the *committed* `dist/`.

## Follow-ups

### This repo's board (virta, `project:tosijs`)

- [ ] **(unverified, minor, correctness)** `StyleSheet` in-place reuse (#4161) covers only a *connected* sheet (`src/css.ts:556`). Run `StyleSheet('theme', proxyA)`, then `sheet.remove()`, then `StyleSheet('theme', proxyB)`. `getElementById` misses the detached element, so a new `<style>` is created, while proxyA's observer keeps regenerating the detached sheet and calling `notifyStylesheetChange`. Removing a sheet already behaved this way before this release, but the new doc says the old proxy "stops driving the sheet", which holds only while the element is attached. Fix: key the observer by id (`Map<string, Listener>`) so a later call with the same id always unobserves the earlier one. The alternative is to narrow the doc sentence. Verify first.
- [ ] **(unverified, nit, blast-radius)** #4160 delegation reaches only shadow roots that `Component` attaches, and `delegateShadowRoot` is not exported. Consumers who call `attachShadow` themselves still get the silent non-composed gap. The docs already state this scope. Export `delegateShadowRoot` only if a real consumer asks for it.
- [ ] **(from B1)** Record in the 1.10.12 AAR that the #4160 tests were written in Happy DOM, which does not model slotted event paths. Like the documented `getBoundingClientRect` trap, this is an environment-suppressed assertion. Consider adding "slotted events don't traverse the shadow root" to the Happy DOM limitations in CLAUDE.md.
