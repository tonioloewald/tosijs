## Findings

### Minor

**1. [security, CONFIRMED] The publish "Wait for approval" step ends GREEN on timeout, so the run can succeed without verifying the published bytes.** `.github/workflows/publish.yml:259`
- After 60 minutes with no approval, the step now writes `approved=false`, prints a `::warning::` and exits 0.
- "Verify what shipped", "Consumer smoke test (from the registry)" and "Summary" are all gated on `inputs.verify_only || steps.wait.outputs.approved == 'true'`, so they skip and the run ends **success**.
- **Late approval goes unchecked.** If the maintainer approves after the timeout, nothing checks the integrity of the published bytes against the staged tarball, or whether `latest` moved on a prerelease, unless someone dispatches `verify_only` by hand. 1.10.5 had to be verified by hand for exactly this reason.
- **A registry outage looks like "not approved yet".** `curl -fsS … | node` is the condition of an `if`, so `set -e` does not catch a curl failure. An hour of DNS or 5xx failures produces the same green "awaiting approval" outcome as an unapproved version. Before this change, that outcome was red.
- **Why it stays minor:**
  - The step summary is honest about what did not happen.
  - npm 2FA approval is the real authorization gate, and direct publish is disabled on the Trusted Publisher.
  - This verification only detects problems; it does not authorize anything.
- The change was deliberate: a red timeout used to email a false CI failure.
- **Fix:**
  - Keep "timeout is not a failure", but make the outcome distinguishable from a verified run, either through a distinct job output or annotation, or by recording that a `verify_only` dispatch is still pending.
  - Count curl failures separately, and fail red if the registry was never reachable during the window.
  - Make the fix in the shared template first. This file is a byte-identical copy of `../tosijs-coding-practices/templates/publish.yml`.

**2. [blast-radius, (unverified)] The brace-expansion fix landed only in tosijs; sibling repos still resolve vulnerable versions.** `package.json:131`
- The lens reports from `bun audit`:
  - `../tosijs-ui` (origin/main c04cb96f3) still overrides to `>=5.0.9` and resolves 5.0.9: 3 advisories (2 high, 1 moderate). It builds through the same audit guard (default `fail`), so its next build will be refused.
  - `../tjs-lang` resolves 5.0.9 and 2.1.4: 10 vulnerabilities (6 high), including the 2.x line (`<2.1.6` / `<2.1.7`). A `>=5.0.12` floor does not cover the 2.x line.
- The tosijs CHANGELOG names two advisories, but **5.0.12 is the version that fixes the third, GHSA-q2hr-2g5m-vwhr** (moderate, `<5.0.12`). Someone copying the CHANGELOG's reasoning would pick the wrong floor.
- This is not a tosijs release blocker: it is a dev dependency, nothing ships, and the failure in the siblings is loud.
- Sanity-check by re-running `bun audit` in each sibling before acting.
